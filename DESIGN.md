# CRITERIA experience specification and work plan

Status: historical experience specification for the initial overhaul, updated with the shared two-sided Home and Criteria discovery route. The current code determines shipped behavior; `FRONTEND.md` and `BACKEND.md` document its routes and contracts. The verification section distinguishes local review from external-service testing.

## Product, routes, and roles

CRITERIA is a two-sided Portuguese property marketplace. Sellers post properties; buyers post their criteria for eligible sellers to discover. Matching works in both directions. Conversations connect a buyer and seller around a listing or criteria post. A member may have a buyer, seller, or both role. Buyers discover properties and publish criteria. Sellers discover criteria and publish properties. Both-role members can do both. Owners can see and edit their own posts even after changing roles; publishing or republishing requires the relevant current role.

Routes are shared Home `/`, sign-in/up, forgot/reset password, OAuth callback, onboarding, property-only results `/feed`, protected Criteria results `/requests`, Create `/create`, Inbox `/inbox` and `/inbox/:id`, Profile `/profile`, Settings `/settings`, public email/deletion confirmation pages, browser privacy information `/privacy`, public active-property detail `/listing/:id` and its protected edit route, and protected criteria detail `/criteria/:id` and edit. Protected direct links preserve the intended destination through sign-in and onboarding. Results URLs preserve keyword, filters, sort, page, list/map view, and map bounds; property results additionally preserve selected district/municipality.

| Journey | Signed out | Buyer | Seller | Both |
| --- | --- | --- | --- | --- |
| Home and property results | Search by district, municipality or keyword; view active listings and details | Same public discovery; contact seller on another user's listing | Same public discovery; publish properties | Same public discovery; publish properties and contact other sellers |
| Criteria and criteria details | Sign in; seller role then required | Own criteria only; explain the role restriction on another post's link | View eligible criteria and contact another buyer | View eligible criteria and contact another buyer |
| Create | Sign in and finish onboarding | Criteria post | Property listing | Choose either post type |
| Edit/archive/republish | Sign in | Own posts remain editable and archivable; republish needs the relevant role | Same ownership rule | Same ownership rule |
| Inbox/profile | Sign in | Participant threads and owned posts | Participant threads and owned posts | Participant threads and owned posts |

The core property journey is: choose Properties on Home, search, open a filtered result, inspect its detail, sign in if contact is needed, and return to the same result URL. A direct property detail link has a safe results fallback. The criteria journey uses the same Home field after switching to Criteria, continues through the protected `/requests` results page, and returns to the same result URL after opening a detail. A buyer-only member receives role guidance there; a guest reaches sign-in with the destination preserved. A role change does not remove ownership access to existing drafts or archived posts, but does limit new publishing.

## Reference interpretation

The initial reference images suggest strong photo-led cards, concise grouped filters, map/list switching near the results, spacious details, and an editorial type hierarchy. Later marketplace references suggest a compact header and immediately usable search form. They are interaction references, not assets or pixel targets. Keep CRITERIA's forest green and sand and its two-sided product model. Home is a working index into property and Criteria discovery. A property photograph fills the Home backdrop, with forest shading protecting the search controls. It adds atmosphere without implying a specific listing. Home contains no property or criteria cards.

Home is shared by guests and members. Its accessible location suggestions cover 18 mainland districts, two autonomous regions and all 308 municipalities on every screen size. In Properties mode, selecting a place or entering a keyword leads to public property-only results. In Criteria mode, the same entry becomes a text search on `/requests`. On desktop, place shortcuts and the district/region directory follow the selected mode; the initial set stays compact, with the rest behind an expansion control. Phone Home keeps the search surface alone. The mode is stored in the Home URL so Back restores it. Desktop Home has one direct CTA for publishing criteria; Create and Profile remain the phone paths to a member's own criteria. Create shows post kinds the current role can publish, and `/create?type=criteria` preselects the buyer form when allowed. Profile shows owned active and archived posts from any prior role. Criteria discovery and messaging remain role protected. Server authorization is authoritative. A forbidden direct link should explain the role requirement; a missing post should explain that it is unavailable. List and map share filter state. Card-opened details return to saved result URLs; browser back/forward must reproduce result controls.

## Design foundation

`frontend/src/index.css` owns HSL color tokens and shadows. `frontend/tailwind.config.ts` maps those tokens to Tailwind utilities. `frontend/src/design-basis.css` owns shared composition classes. Existing `src/components/ui` primitives are the component foundation; Radix Slot and class-variance-authority are already present for the button API. Add a shadcn/ui primitive only when it solves a specific accessibility or interaction need, and restyle it with these same tokens. Do not introduce a second palette or reset.

| Foundation | Rule |
| --- | --- |
| Color | Forest green `#344e41` for actions, deep green `#1a2e22` for navigation, sand `#f5f0e8` and warm paper for canvases, white raised surfaces. Home shades the photograph with deep forest, uses sand for the search action and criteria CTA, and reserves restrained clay for the selected mode and place-link details. Dark mode uses deep forest surfaces, warm text, sage links and the same action green. Semantic status tokens require readable foreground contrast. |
| Type | One self-hosted IBM Plex Sans variable family for interface and display. App screen titles 28–44px, sections 18–20px, body 14–16px with comfortable leading, metadata 12–13px. Prices use tabular numerals. Use tighter tracking selectively on large headings; avoid all-caps prose. |
| Space | 4px rhythm; page gutters 20px on phones and 32–40px on wide screens; 24–32px between sections. Reading width stays restrained. Let fine rules and spacing group information before adding another panel. |
| Shape/depth | Controls have about 4px corners, cards and panels 6–8px, property photography 0–2px. Keep avatars and map location dots circular because their shape carries meaning. Use a hairline border or an offset soft shadow for elevation, rarely both. Avoid pill treatments for ordinary navigation and actions. |
| Images | 4:3 listing cards, generous detail hero with a nearly square edge, `object-cover`; a designed fallback when no photo exists. Alt text reflects content. |
| Interaction | At least 44px targets, visible focus, names for icon controls, `aria-pressed` for choices, dialog focus restoration, disabled/loading/error/retry states. |
| Motion | Short 150–200ms transitions and `prefers-reduced-motion`; no forced smooth scroll. |
| Breakpoints | Under 768px the Home photograph fills the hero backdrop; the forest scrim darkens its lower area behind full-width, thumb-friendly search controls. Secondary Home sections are hidden. Signed-in members have a brand/profile header and three bottom tabs, while guests have account actions. At 768px+ the photograph remains visible on the right, supporting Home sections return, and the app uses top navigation. At 1024px+ use structured detail/form/profile layouts. Wide screens add columns without stretched text. Capacitor follows viewport width. |

The current app uses a **mobile-first Operate layout** with moderate density and restrained motion. The visual language takes cues from architectural plans and property catalogues: straight photo edges, fine dividing rules, clear numerals, and a few strong forest-green planes. It should feel precise and warm rather than generic or ornamental. Phones should reach the primary task in the first viewport: search on Home/results, a post form on Create, owned posts on Profile, account sections on Settings, and conversations in Inbox. Desktop adds parallel reading space and navigation without changing the task order. `screen-wrap`, `screen-heading`, `screen-intro`, `section-title`, and `field-note` in `design-basis.css` define the shared screen rhythm; components should use semantic color tokens from `index.css`. The button, input, and textarea primitives set common shape, focus, and minimum touch size.

Use one clear heading per screen, a short supporting line only when it helps, and content-led sections. Property cards lead with photography, full price, title, location, and facts. Detail pages show the listing or request title as the page heading and keep the relevant contact action reachable above the phone navigation. Long forms use full-width phone fields, visible sections, accessible choice state, and an error summary that receives focus after invalid submission. Account and security feedback is announced to assistive technology. Avoid decorative pre-headings, repeated icon-card grids, nested panels, and motion that shifts a control while someone is trying to use it.

The existing roof-and-C mark from `frontend/public/icon-192.png` identifies the app in the shell and on Home. Settings offers Light, Dark, and System; System follows OS changes. The preference persists locally, and a synchronous document-head script applies it before React paints. The `dark` class changes semantic CSS variables in `index.css`; Tailwind uses the same variables, so components do not need a parallel palette. The interface defaults to `pt-PT`; an English choice is saved locally and updates the document language to `en-GB`. On phone widths, Settings separates account controls from an About Criteria tab for privacy, terms and contact email; desktop browsers put the language switch in the top bar. `map-theme.css` gives maps the same forest-and-paper surfaces, 44px controls, readable light/dark raster treatment, and distinct property, buyer, and location pins. Only the default OpenStreetMap raster pane is filtered; configured tile providers retain their own colors and attribution. A nationwide map focuses mainland results first when most results are there, with a visible Show all Portugal control for islands; this never changes the result filters. Security changes use explicit confirmation states and one-use email links.

Use plain, accurate Portuguese copy by default: “Arquivar anúncio”, “Voltar a publicar”, “Enviar mensagem”, “Critérios”. Provide matching English copy through the language preference. State that sellers can discover criteria while buyers can manage their own. Mark a nonowner map as approximate. Empty states suggest the next action. Prices are full euro amounts and areas use m².

## States and verification matrix

Every route needs loading, populated, empty, error and permission states. Forms additionally need invalid, submitting, success, archive/edit and upload-failure states. List/map must cover no imagery, no tiles, no results and long titles. Local review mode offers buyer/seller/both, owned/other/archived posts, slow/error/empty responses, signed-out, and incomplete onboarding. Check 320px, 390px, 768px, 1024px and 1440px, plus landscape tablet; keyboard-only use, screen-reader order/names, 200% zoom, touch/safe areas, reduced motion and back/forward.

Local Vite review mode opts in with `?review=1`. It uses in-memory fixtures and mutations, blocks real backend writes and unknown requests, and is gated by compile-time `DEV`. Production bundles are checked for review markers. It supports layout and journey review; real auth, database, media and native integrations require staging tests.

Review matrix: signed-out and unfinished-onboarding direct links; guest and member Home property search by keyword, district and municipality; Home Criteria keyword search with sign-in return; compact place shortcuts and directory expansion; public property results/detail and protected contact; buyer, seller and both-role `/requests` states; own, other and archived listings/criteria; new and edited posts; matching and no matches; inbox empty/thread/send/error; list and map with active filters, pagination and no results; photos present/missing/upload failure; and slow or failed requests. Confirm the URL, focus target, visible loading/error copy, and role permission at each transition. Run the same journeys at phone, tablet and desktop widths and in the native WebView where available.

Theme and layout checks additionally cover Light/Dark/System on guest/member Home and auth, property results list/map/filter dialog, both detail types, create/edit, Inbox and Profile. Verify theme persistence on reload and OS preference changes, map label readability, keyboard focus and contrast on every surface. At 320px and 390px check Home search, the member Profile affordance, centered Create tab and safe-area padding; at 768px, 1024px and 1440px check nav fit, horizontal overflow, page gutters, grid density and split-detail balance. The development fixture illustrates structure and states; production photos and external identity providers still require their own smoke tests.

## Priorities and acceptance gates

1. **Foundation/data (P0):** server search/count/sort/bounds, role/ownership gates, location privacy, upload keys, onboarding/OAuth. Gate: schema validation, server typecheck/tests, direct-link safety.
2. **Navigation/discovery (P0):** one responsive navigation model, shared mode-switching Home search, URL-backed public property results and protected Criteria results with list/map/filter/search/sort/page. Gate: guest and member searches, seller/buyer role states, direct links and back/forward reproduce results across phone/tablet/desktop.
3. **Create/detail/profile/messaging (P0/P1):** type-aware fields, photo upload, archive/republish, matches, contact, Inbox, owned states. Gate: buyer/seller/both and own/other/archived journeys; no inert CTA.
4. **Auth/polish (P1):** sign-in/up, onboarding, recovery, native callback, design states and accessibility. Gate: keyboard, zoom, network error and native smoke checks.
5. **Release checks:** frontend/server typecheck, lint, tests and build; staging migration and external-service smoke test; production mock exclusion. Run migrations before server deploy.

## Dependencies, risks, and owner decisions

- Run migrations `0003`, `0004` and `0005` before deploying server changes that read their columns. Existing Google users without an onboarding-completed marker may be asked to complete onboarding once; existing password users are backfilled as complete. `0005` supports account changes, immediate access revocation and durable image erasure jobs.
- Recovery needs Resend credentials, a verified sender and frontend origin. Google requires exact callback registration and a matching `FRONTEND_URL` per environment; preview and LAN origins need their own trusted configuration. One-time OAuth state/code currently lives in process memory, so multiple API instances need shared short-lived storage.
- Browser image PUTs need R2 CORS for the site origin. The app re-encodes photos to remove GPS and other camera metadata, but the direct R2 upload flow does not enforce this for other clients; a server-side image pipeline is needed for that guarantee. Removed photos remain publicly accessible to anyone with their old URL. Reference tracking and an asynchronous cleanup job are needed before deletion can be reliable.
- Public location labels and search recognize Portuguese municipalities, districts and autonomous regions from a static index, but existing posts store free-form geocoder labels rather than administrative IDs. Unknown places fall back to “Portugal” or “Approximate area”; a listing whose geocoder label omits its municipality/district can be missed by structured location search, and a district can still be mistaken for a city in a public label. Add structured locality fields from geocoding for fully reliable national coverage while keeping street-level addresses owner-only. Owners can still type an address into the title or description, so public copy should remind them not to include private location details there.
- Official OSM tiles solved the broken review map. Select a compliant production tile provider and budget before scale. Map results are capped at 200 posts and nearby pins are grouped visually at broad zoom levels; larger result sets would need server-side aggregation.
- Criteria post data (`buyerPosts` in the API) remain seller-gated and absent from public Home and property results; Home offers a sign-in path to protected discovery. Any future change to the data policy must update both UI and server access rules.
